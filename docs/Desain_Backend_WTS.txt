Status penting

                         cancelled, closed

 offers.status         : pending, accepted, rejected, countered, expired

Constraint kunci yang dipaksa DB
 - Domain email @nusaputra.ac.id (trigger pada auth.users) + cek banned_emails
 - username ^[a-z0-9_]{3,20}$ unik
 - Tag maks 2, gambar postingan maks 5, gambar produk maks 10 (trigger)
 - Satu vote per user per target (PK komposit); tidak bisa vote konten sendiri
 - Satu kesepakatan aktif per produk (UNIQUE partial index market_chats_one_deal)
 - Satu tawaran pending per chat (UNIQUE partial index offers_one_pending)
 - Jual/sewa: rent_unit wajib jika sewa; defect_note wajib jika second
 - Kedalaman komentar maks 2; harga > 0 dan <= Rp100.000.000
 - hard_delete_at = expires_at + 15 hari (default 30 + 15 = 45 hari)

3. KEPUTUSAN DESAIN KUNCI (menutup celah analisis sebelumnya)
================================================================================
 K1. Tabel dasar privat, konten dibaca lewat VIEW.
     RLS tidak bisa menyembunyikan KOLOM, sehingga posts/comments/profiles tidak
     boleh dibaca langsung oleh klien. Klien membaca posts_public,
     comments_public, profiles_public (view berjalan sebagai owner, author_id
     diganti NULL bila anonim). Ini menjamin anonimitas walau klien memodifikasi
     query.
 K2. Anonim tidak bisa bocor lewat gambar.
     Nama file gambar postingan/produk = UUID acak TANPA user id. Kepemilikan
     dicatat di storage.objects.owner_id dan diverifikasi trigger saat
     post_images/product_images dibuat.
 K3. Alias komentar anonim.
     Komentar tidak anonim (sesuai brief). Hanya pemilik postingan anonim yang
     berkomentar di postingannya sendiri tampil sebagai "Penulis (Anonim)"
     (kolom is_anonymous_op); author_id-nya disembunyikan.
 K4. Perubahan bernilai bisnis lewat RPC security definer (atomik + validasi).
     Klien TIDAK punya hak INSERT/UPDATE langsung ke: posts (insert),
     products (insert/status), market_chats, offers, conversations,
     notifications, user_strikes. Mencegah status transaksi dimanipulasi.
 K5. Guard berlapis: GRANT kolom (UPDATE hanya kolom tertentu) + trigger guard
     (transisi status, jendela edit 24 jam/5 menit) + RLS.
 K6. Konteks sistem: is_internal() = auth.uid() null (cron/service) ATAU flag
     wts.internal (diset RPC) ATAU pg_trigger_depth() > 1. Guard dilewati di
     konteks ini.
 K7. Penghapusan file lewat ANTRIAN. Menghapus row storage.objects lewat SQL
     tidak menghapus file fisik. Trigger memasukkan path ke file_delete_queue,
     Edge Function purge_files menghapus via Storage API (retry maks 5x).
 K8. Hapus akun = RPC delete_my_account (hapus auth.users, cascade semua data
     + antrean file); tidak perlu Edge Function. Akun suspended/banned tidak
     boleh menghapus diri (cegah kabur dari sanksi). Akun banned tidak ikut
     dihapus job 6 bulan, dan hash emailnya ada di banned_emails.
 K9. Rate limit di DB, konfigurasi di app_config.rate_limits (ubah tanpa rilis app).
 K10. Staf TIDAK dapat membaca isi chat. Bukti laporan = snapshot 20 pesan
      terakhir yang disimpan pada reports.snapshot (dihapus 30 hari setelah
      ditangani). Identitas posting anonim hanya via RPC admin_reveal_author
      (admin) dan tercatat di audit_logs.
 K11. Produk "sewa" memakai status sold di MVP (label UI "Disewa"). Fitur
      "sewakan lagi" (relist) masuk backlog.
 K12. Produk yang dihapus penjual = soft delete 3 hari (agar chat berjalan bisa
      ditutup rapi), lalu hard delete. Postingan linimasa yang dihapus penjual
      langsung hard delete (sesuai brief).
 K13. Kesepakatan menggantung > 14 hari tanpa aktivitas dibatalkan otomatis
      (produk kembali tersedia) supaya produk tidak "dipesan" selamanya.
      (Aturan tambahan; ubah di job_cleanup_chats bila tidak diinginkan.)

================================================================================
6. KATALOG EDGE FUNCTION
================================================================================
 Autentikasi semua fungsi internal: header x-wts-secret = vault
 'edge_shared_secret' (verify_jwt=false). Jangan memanggil dari klien.

 6.1 send_push  [kode ada]
   Pemicu : trigger DB notifications INSERT -> pg_net -> POST /send_push
   Input  : { notification_id: uuid }
   Proses : baca notifikasi (lewati bila sudah pushed_at), cek notif_prefs
            pengguna & status akun, ambil device_tokens, kirim FCM HTTP v1
            (judul/isi generik, tanpa isi pesan chat), hapus token
            UNREGISTERED/INVALID, set pushed_at.
   Output : { sent: n } | { skipped: ... }
   Secrets: EDGE_SHARED_SECRET, FCM_SERVICE_ACCOUNT (JSON), + SUPABASE_URL &
            SERVICE_ROLE_KEY (otomatis tersedia).
   Error  : kegagalan FCM tidak menggagalkan transaksi utama (async). Jika
            gagal total, pushed_at tetap NULL -> dapat dijadwalkan ulang.
   Batas  : free tier 500 ribu invokasi/bulan. Throttle push chat sudah ada di
            trigger (maks 1 notifikasi/2 menit/chat).

 6.2 purge_files  [kode ada]
   Pemicu : pg_cron tiap jam (menit ke-20)
   Proses : baca file_delete_queue (attempts < 5), kelompokkan per bucket,
            storage.remove(), hapus baris antrean; gagal -> attempts+1;
            attempts >= 5 -> catat audit_logs 'purge_failed' lalu buang.
   Output : { deleted, failed, dropped }
   Idempoten: aman dijalankan ulang.

 6.3 sweep_orphans  [spesifikasi; belum ada kode]
   Pemicu : pg_cron mingguan (Minggu 04:00 WIB)
   Tujuan : hapus file yatim akibat unggah gagal/postingan tak jadi dibuat.
   Proses : daftar objek per bucket yang umurnya > 24 jam dan tidak dirujuk:
            post-images (post_images.path), product-images (product_images.path),
            chat-images (messages.meta->>'path'), avatars (profiles.avatar_path);
            hapus via Storage API; batasi 500 objek per eksekusi; log jumlah.
   Catatan: jangan hapus objek < 24 jam (pengguna mungkin masih menyusun post).

 6.4 validate_upload  [opsional, fase 2]
   Pemicu : Database Webhook pada storage.objects INSERT
   Tujuan : cek magic bytes (JPEG/PNG/WebP asli, bukan file lain berekstensi
            gambar) dan batas dimensi; hapus + catat bila tidak valid.

 Tidak perlu Edge Function untuk: validasi domain email (trigger DB),
 hapus akun (RPC), laporan/moderasi (RPC), job retensi (SQL + pg_cron).

                                      lama, snapshot laporan >30 hari

 wts_sweep_orphans    Minggu 21:00    panggil Edge Function sweep_orphans

 Aturan retensi chat -> implementasi
  - DM: messages.delete_at = created_at + 3 hari (trigger insert)
  - Market, negosiasi: market_chats.delete_at = aktivitas terakhir + 3 hari
    (diperbarui trigger tiap pesan)
  - Market, sepakat lalu terjual: delete_at = sold_at + 7 hari (mark_sold)
  - Market, chat lain pada produk terjual: delete_at = sold_at + 3 hari
  - Market, batal: delete_at = cancelled_at + 3 hari
  - Produk expired/dihapus: chat negosiasi ditutup, delete_at +3 hari

8. SPESIFIKASI CI/CD (GitHub Actions)
================================================================================
 8.1 Lingkungan
   - dev lokal : supabase start (Docker) + app Flutter dengan --dart-define
   - staging   : project Supabase #2 (gratis, maks 2 project di free tier)
   - production: project Supabase #1
   - GitHub Environments: staging, production (production: Required reviewers)

 8.2 Alur cabang
   fitur/* -> PR -> main (squash). main selalu dapat dibuild & di-deploy.
   Rilis: tag vX.Y.Z (semver) pada main.

 8.3 Workflow
 ci.yml (PR & push main)
   job flutter  : pub get -> dart format (gagal bila berbeda) -> flutter analyze
                  --fatal-infos -> flutter test -> build APK debug (kunci dummy)
   job database : supabase start -> db reset (semua migrasi + seed dari nol) ->
                  db lint (gagal pada error) -> supabase test db (pgTAP)
   job functions: deno lint + deno check semua Edge Function
   Merge diblokir bila ada job merah (Branch protection: required checks +
   1 review).

 deploy-backend.yml (push main yang mengubah supabase/**, atau manual)
   staging    : link -> db push -> functions deploy (otomatis)
   production : menunggu persetujuan -> db push --dry-run (tampil di log) ->
                db push -> functions deploy
   concurrency : satu deploy pada satu waktu.

 release-app.yml (tag v*)
   decode keystore dari secret -> flutter test -> build APK release
   --obfuscate --split-debug-info -> unggah simbol debug (90 hari) -> GitHub
   Release (APK + changelog otomatis). Opsional: Firebase App Distribution.

 ops.yml (terjadwal)
   keepalive harian : POST rpc/ping agar project free tier tidak di-pause
   backup mingguan  : pg_dump schema public (via session pooler) -> enkripsi
                      GPG AES256 -> artifact 30 hari. Untuk jangka panjang, unduh
                      artifact berkala ke penyimpanan tim.

 8.4 Secrets (Settings > Secrets, per environment)
   SUPABASE_ACCESS_TOKEN, SUPABASE_DB_PASSWORD, SUPABASE_PROJECT_REF,
   SUPABASE_URL, SUPABASE_ANON_KEY (anon key memang publik, tetap simpan sebagai
   secret agar mudah diganti), BACKUP_DB_URL, BACKUP_PASSPHRASE,
   ANDROID_KEYSTORE_BASE64, ANDROID_KEYSTORE_PASSWORD, ANDROID_KEY_PASSWORD,
   ANDROID_KEY_ALIAS, (opsional) FIREBASE_APP_ID, FIREBASE_SERVICE_ACCOUNT.
   Secrets runtime Supabase (di dashboard/CLI, BUKAN GitHub):
   supabase secrets set EDGE_SHARED_SECRET=... FCM_SERVICE_ACCOUNT='{...}'
   Vault database: edge_base_url, edge_shared_secret (lihat 0004_cron.sql).
   service_role key TIDAK PERNAH masuk klien/repo/CI selain deploy.

 8.5 Kebijakan
   - Semua perubahan skema lewat file di supabase/migrations (buat dengan
     `supabase migration new nama`). Dilarang mengubah skema production lewat
     Studio. Migrasi yang sudah di-merge tidak diedit; koreksi = migrasi baru.
   - Versi aplikasi: pubspec version + tag; app_config.min_app_version untuk
     force update.
   - Menit gratis GitHub (repo privat ~2.000 mnt/bulan): build Flutter ~8-12
     mnt; gunakan concurrency cancel-in-progress (sudah ada) dan cache.
   - Backup keystore Android di tempat aman (hilang = tidak bisa update app).
